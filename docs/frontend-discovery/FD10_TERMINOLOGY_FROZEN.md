# FD-10 — TERMINOLOGY: CANONICAL SEMANTIC VOCABULARY

# STATUS: FROZEN — FOUNDER APPROVED 2026-08-15
# SELECTED: OPTION A — RESOLVE NOW WHERE SEMANTIC TRUTH IS SUFFICIENT

> **Correction to the brief that produced this decision.** The brief classified `Cancel` / `Dismiss` / `Close` / `Discard` as **pure synonyms**. That premise was **wrong** and is corrected in §4: they represent four different user intentions and are governed semantically, not collapsed.

---

## 1. Language doctrine

> **SEMANTIC TRUTH FIRST. VOCABULARY SECOND.**

A word survives only when the underlying product concept survives.

- Do **not** solve duplicated architecture through copy changes.
- Do **not** collapse genuinely different concepts merely to reduce vocabulary count.
- Do **not** preserve synonymous product nouns merely because both already exist.

## 2. Group 1 — settled by frozen semantics

| Concepts | Ruling |
|---|---|
| **Thread** and **Space** | both survive — distinct |
| **Meeting**, **Room**, **Live** | all survive — distinct |

| **Person / Institution / Membership / Acting Context / Presence** | remain distinct — do not flatten |

## 3. Retry

> **Canonical actionable vocabulary = `RETRY`.**

For the semantic action *the previous operation failed → attempt it again*. Retires arbitrary `Try again` / `Retry` drift (29 vs 22 today).

This does **not** prohibit natural explanatory copy containing ordinary language.

## 4. Cancel / Dismiss / Close / Discard — four distinct families *(premise corrected)*

> **DO NOT collapse these four into one word. They are not semantically identical.**

| CTA | Semantic meaning |
|---|---|
| **CANCEL** | stop or withdraw an operation/intent that has **not completed** |
| **DISMISS** | remove an item/prompt/attention projection from current attention **without implying the underlying object was deleted** |
| **CLOSE** | close a view, panel, modal, sheet or presentation surface **without implying cancellation or deletion** |
| **DISCARD** | deliberately abandon **unsaved/uncommitted** composition or draft work |

Use each only where its meaning is true.

> **The drift to eliminate is arbitrary interchangeability — not vocabulary diversity itself.**

Enforced later by the Product Language Authority as semantic CTA families.

## 5. Correspondence vs Conversation / Message

> **CORRESPONDENCE SURVIVES AS A DISTINCT GOVERNED COMMUNICATION FORM.** It must **not** survive merely as another architectural name for DM/Message/Thread.

| Concept | Meaning |
|---|---|
| **MESSAGE / DM** | conversational interpersonal communication |
| **THREAD** | focused conversation continuity |
| **CORRESPONDENCE** | deliberate/formal communication with stronger **institutional/documentary continuity and governance semantics** |

> **⚠ The surviving word does NOT protect the current architecture.**

Audit `correspondence` · `direct_threads` · the three thread screens · repositories · routes · conversation implementations against this distinction. **If the current Correspondence implementation is merely duplicate messaging architecture, converge/rebuild the mechanics while preserving the distinct governed product semantics.** Shared communication infrastructure is expected; distinct semantic ownership remains.

## 6. Correspondence — two-layer naming *(approved with condition)*

"Correspondence" may survive as **both** a governance/domain word **and** a product word — **only where the user is actually engaging the distinct governed Correspondence capability**.

> **Do not maintain `internal name = Correspondence` / `user experience = generic conversation` by accident.** Any internal/product naming split must be **deliberate and documented**. **The current accidental split is drift and must not be preserved for compatibility.**

## 7. Works vs Posts

> **POST remains the canonical publication/content noun** where the object is actually a Post.
> **WORKS must NOT survive as a competing noun/model for the same canonical publication object.**

"Works" survives **only** if reconstruction proves a distinct semantic purpose — e.g. *a curated/aggregated projection of a person's or institution's body of work*. In that case: **Works = projection/collection · Post = canonical publication object.**

**Works must never become a second publication authority.** If they are the same concept, **retire/converge the duplicate Works model**. Contradicting evidence is brought forward in the owning chapter.

## 8. Presence

> **PRESENCE SURVIVES AS THE AUTHORITY / DOMAIN CONCEPT. Do NOT globally rename Presence to Availability** — Availability is only *one possible human projection* of Presence.

Presence remains **contextual projection ≠ identity**.

Ordinary UI expresses the **meaningful human state** rather than exposing "Presence" as a technical noun. Illustrative only, **not a frozen taxonomy**: Available · Away · Active · In a meeting · Offline.

> **Local surfaces must not infer or invent presence independently** — use the canonical Presence authority.

## 9. Follow vs Connect

> **FOLLOW and CONNECT are DISTINCT RELATIONSHIP SEMANTICS.**

| Term | Meaning |
|---|---|
| **FOLLOW** | **asymmetric** interest/subscription — no reciprocal acceptance required |
| **CONNECT** | **reciprocal** person-to-person relationship, requiring an actual reciprocal relationship lifecycle if/when that capability exists |

- Do **not** use them interchangeably.
- Do **not** rename Follow to Connect for warmer language.
- Do **not** introduce a Connect CTA simply because the word is now defined.

> **Connect becomes user-visible only if/when the underlying reciprocal capability is legitimately constructed and approved.** Recorded as **semantic vocabulary for a possible distinct relationship — not an implementation obligation** unless the roadmap separately establishes that capability.

## 10. Verification language

> **Do NOT invent one generic user-visible "Verified" label.**

Use the frozen backend verification classes as semantic source authority. Before final labels are frozen, map each class to: **what was actually verified · who/what granted or established it · where it has user value · where it should remain hidden · what human-readable label communicates that truth without flattening the layers.**

> Recorded as a **constrained Product Language implementation obligation — NOT an unresolved semantic architecture decision.** Do not invent final verification names merely to close FD-10.

Contextual language names the actual obligation (invitation · missed interaction · mention requiring attention · approval/action required). `UNSEEN`/`RESOLVED`/`DISMISSED`/`EXPIRED` drive behaviour and appear **only where useful to comprehension**. |

## 15. Product Language Authority scope

FD-10 does **not** hard-code all copy now. It freezes **canonical semantic vocabulary and distinctions**.

The Authority governs: canonical product nouns · semantic CTA families · prohibited synonym drift · context-sensitive human language · governance-to-product translation · terminology enforcement where justified.

> **Do not turn it into a centralized database of every sentence in the application.**
