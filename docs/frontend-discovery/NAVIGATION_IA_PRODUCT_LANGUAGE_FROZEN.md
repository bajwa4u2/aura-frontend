## 1. Core decision

The current navigation architecture is **not the design constraint**. The drift is **not** solved by cleaning up today's route tree · reorganising today's menus · preserving mirrored institution navigation · exposing backend modules as navigation · renaming tabs without resolving their semantics.

> **ONE COHERENT INFORMATION ARCHITECTURE + FEW STABLE PRIMARY DESTINATIONS + CONTEXTUAL OBJECT-LOCAL NAVIGATION + CAPABILITY-ADAPTIVE ACTIONS + CANONICAL PRODUCT LANGUAGE.**

Organised around **what people are trying to accomplish and the objects they work with** — not historical implementation structure.

---

## 2. Governing navigation principle

> **USERS NAVIGATE TO OBJECTS AND INTENTIONS, NOT ORGANIZATIONAL CHARTS OR BACKEND MODULES.**

Navigation answers: Where am I? · What am I working with? · What deserves my attention? · What can I do here? · How do I get back? · Who am I acting as, where that matters?

**It must not require understanding Aura's internal service/domain architecture.**

---

## 3. Primary navigation — deliberately small and stable

> **⚠ EXACT PRIMARY DESTINATIONS ARE NOT FROZEN BY THIS DECISION.**

The final primary IA is to be derived later from: frozen product semantics · reconstructed domain ownership · global-market research · user journeys · frequency/importance · object relationships · attention architecture · acting context · capability-adaptive experience.

- Do **not** preserve a primary destination merely because it currently exists.
- Do **not** add one merely because a backend capability exists.

---

## 4. Contextual depth — objects own their depth

| Object | Owns |
|---|---|
| **Space** | its conversation/content · people/participation · realtime where legitimate · object-local management where authorised |
| **Thread** | its conversation · participants/context · realtime belonging to that Thread · relevant actions |
| **Meeting** | its own Meeting lifecycle and contextual navigation |
| **Institution** | institution identity/context · institution-relevant capabilities · contextual management where authorised |
| **Person** | canonical identity · relevant relationship · appropriate actions |

> **Do NOT push ordinary object-local actions into distant global dashboards.**

---

## 5. Acting context must not duplicate IA

Per frozen **FD-9**: moving from acting personally to acting for an institution **must not produce a second mirrored application/navigation tree**. Acting context changes *representation and available capability*, not the information architecture.

The **~40 mirrored institution routes remain explicit demolition/convergence candidates** (DR4).

---

## 6. Capability-adaptive navigation

Per frozen **Capability-Adaptive Experience**: navigation/actions adapt to `PERSON + ACTING CONTEXT + PRODUCT CONTEXT + BACKEND CAPABILITY + CURRENT STATE`.

> **Do NOT create permanent navigation clutter for capabilities only some people use occasionally.**

A member simply participates in a Space. An authorised operator additionally receives contextual Manage · Invite · Moderate · Start appropriate realtime — **without a separate admin navigation system**.

---

## 7. Primary navigation ≠ every capability

**Do NOT make every feature a tab.** A capability may legitimately live as: contextual action · object-local section · progressive disclosure · Attention action · creation action · management action · search/go-to result · deep-link destination.

> **Navigation prominence must reflect human purpose, not implementation availability.**

---

## 8. Deep-link continuity

Deep links preserve the **most specific legitimate context**: mention → exact post/reply/conversation · message attention → exact conversation · meeting invitation → exact Meeting · room invitation → exact Institution Room · Thread realtime attention → owning Thread · Space attention → relevant location in the Space · relationship attention → relevant Person/context.

> **Do NOT redirect to generic landing pages and force rediscovery of the object/action.**

---

## 13. Canonical Product Language Authority

Accumulated CTA/naming drift must be resolved **systematically, not one screen at a time**. Identified examples include Works/Posts · Presence/Profile · Correspondence/Message, plus others found in audit.

A **Canonical Product Language Authority** is to be established during later architecture/design, governing product-facing: nouns · verbs · CTA families · state terminology · navigation labels · action labels · contextual variants · relationship terminology · participation terminology.

---

## 14. Language governing rule

> **CONVERGE SYNONYMS. PRESERVE GENUINE SEMANTIC DISTINCTIONS.**

- If **Works** and **Posts** are the same canonical concept → one term ultimately survives.
- If **Presence** and **Profile** are genuinely distinct → both survive with distinct meanings and are **never** used interchangeably.
- If **Correspondence** is a governed communication form genuinely different from DM/Message → both survive because the products differ.

> **Do not choose terminology because one word sounds newer or cleaner. First establish semantic truth, then canonical language.**

---

## 15. No copy-only fixes for architectural drift

If terminology drift reflects **duplicated architecture**, renaming is insufficient — determine whether the **screens themselves** should converge. Conversely, if two different concepts share one label, **distinguish them**.

> **Language governance must follow product semantics.**

---

## 16. CTA system

Consistent action families **without** forcing identical vocabulary everywhere. A CTA communicates the actual product action.

Illustrative families only — Create · Send · Reply · Publish · Join · Invite · Accept · Decline · Manage · Follow · Start · End · Resolve — **none of which freezes final vocabulary**.

> **SAME ACTION → CONSISTENT LANGUAGE. DIFFERENT ACTION → PRESERVE MEANINGFUL DISTINCTION.**

---

## 17. Action location

Prefer **OBJECT → RELEVANT ACTION**. Avoid *object → navigate to module → navigate to management screen → rediscover object → perform simple action.*

Especially for: profiles · Threads · Spaces · Meetings · Institution Rooms · Attention · participation · member management · institutional actions. Use object-local management and progressive disclosure where practical.

---

## 18. Universal Find / Go-To

Leave room for a modern universal Find/Go-To across legitimate objects (people · institutions · Spaces · Threads · Meetings · relevant communication · others justified during design). Implementation **not frozen**.

> **SEARCH / GO-TO SUPPLEMENTS GOOD NAVIGATION. IT MUST NOT BECOME A PATCH FOR BAD INFORMATION ARCHITECTURE.**

---

## 19. Global-market research (before final IA is frozen)

Research: primary/contextual/object-local/adaptive navigation · command-find experiences · deep-link continuity · mobile and desktop navigation · communication, collaboration and community IA · contextual administration · CTA systems · terminology consistency.

Study: cognitive load · destination count · discoverability · context preservation · progressive disclosure · responsive behaviour · role/capability adaptation · complexity failures.

> **Do NOT copy another product's navigation or terminology.**

---

## 20. Responsive / cross-form-factor

> **The navigation architecture must be conceptual before it is visual.**

Do **not** design a desktop IA and then separately invent a mobile IA. One product architecture adapts across supported form factors — presentation mechanisms may differ; **product semantics, destinations, context and language remain coherent**. Includes the Windows/MSIX Release Client.

---

## 21. Demolition / rebuild consequence

Reconstruction territory: mirrored institution navigation · duplicated route architecture · inconsistent CTA vocabulary · semantically drifting labels · module-oriented navigation · redundant destinations.

**DEMOLISH / CONVERGE / REBUILD AS WARRANTED, preserving valid product behaviour and deep-link requirements.**

> **Do NOT preserve structural drift merely to avoid route migration/refactor. Migration/refactor fear is explicitly removed as a design constraint.**

---

## 22. Representation consequence

Canonical product language must **not** be independently invented by the Release Client if Representation holds conflicting terminology or presentation doctrine. During later language reconstruction: inspect Representation → where genuine drift exists, **bring it forward, resolve canonical meaning, then align repositories**.

> **Do NOT edit Representation during adjudication. Do NOT silently choose one repository's terminology over another.**

---

## 23. Enforcement direction

Investigate: canonical product-language registry · shared CTA primitives · canonical route/object definitions · navigation authority/configuration · architecture tests · source-level gates · restricted raw product labels · documentation contracts.

> **Do not create bureaucracy merely for enforcement. Use the minimum mechanism that actually prevents drift.**
